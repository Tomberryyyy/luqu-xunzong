# 鲁趣寻踪AI大模型应用说明

青岛工学院　熊猫烧香队　｜　赛道三 AI传播工具创新　｜　第六版

鲁趣寻踪在制作过程和产品运行中都使用了AI辅助。我们在这里说明用了哪些工具、由AI完成哪些工作，以及哪些内容需要人确认。本文对应已发布的第六版。

## 制作过程中使用的工具

前期使用扣子编程助手辅助搭建原型，后续使用ChatGPT及Codex协助修改代码、调整界面、排查问题、检查规则，并整理演示和说明材料；豆包用于前期交流及文字参考。开发工具的具体版本未全部留存，因此只列实际用过的工具名称。

我们提出并调整需求，提供景点Excel，试用各版程序，反馈错误，选择界面方案，并逐次确认修改结果。例如，最初的关键词输入不能充分表达“不想爬山”等要求，后来增加自然语言画像和确认区；推荐缺少解释时，又补上资料依据和未知条件的展示。代码、界面和说明材料均有AI辅助，团队负责需求、试用反馈和最终确认。

## 产品实际调用的大模型

第六版演示接入服务使用的模型标识为gpt-6.1-sol，可在本地配置及保存的真实运行记录中核对。后端通过兼容OpenAI Chat Completions的接口调用。该名称记录的是接入服务的模型标识，运行模型可按服务商支持的范围在本地配置中更换。

模型参与两个环节。第一，/api/profile接收用户描述，返回六个维度的偏好与提取依据。第二，/api/copywriting接收用户确认后的画像、景点简介、推荐季节和注意事项，生成结构化标题及短文案。

城市筛选、兴趣匹配、排除条件、冲突检测及候选排序由本地代码规则处理。景点数据由Excel整理，图片使用已有素材链接，产品运行环节没有让大模型生成景点图片或视频，也未使用向量检索RAG。

## 画像提取如何约束

我们要求模型只提取用户明确表达的内容，未提及的维度返回“未说明”，每个已提取维度附上原表述依据。例如，“内向”本身不能推断为怕人多或体力低；“喜欢自己慢慢逛”可以作为独自同行和慢节奏的依据。模型返回后还要经过用户确认，提取不准确时可以直接修改或删除。

## 文案生成如何约束和检查

文案提示词同时传入确认后的画像与景点资料，要求不建议用户明确排除的活动，不编造资料之外的事实。标题目标为15字以内，正文目标为80至120字，并要求只返回JSON，便于页面展示和后续编辑。

后端检查返回内容能否解析为JSON，并用程序字符数检查正文长度；不合格时要求重写，仍失败则显示错误。提示词中的标题长度、事实准确性和排除约束仍需人工复核，不能仅凭格式检查就认定内容正确。

## 人工确认与修改记录

人的干预分布在画像确认、条件冲突修正和文案定稿几个位置。使用者决定哪些偏好用于推荐，对照资料检查推荐依据和文字，再保存修改稿。导出内容保留初稿、修改稿、画像和匹配信息；刷新或开始新探索前，需要自行导出保存，当前没有自动保存历史会话。

## 根据试用反馈做过的修改

早期版本主要按关键词匹配，后来加入六维画像和人工确认；为避免条件被忽略，又增加排除优先、兴趣与排除冲突提示，并把确认后的画像传入文案提示词。对资料不支持的同行、节奏或体力判断，显示未知或待确认，避免为了推荐而补出结论。

第六版进一步保留了匹配说明、人工编辑和导出功能，让用户能看到推荐理由并修改结果。上述改动可结合各版工程、当前提示词与项目修改记录核对。开发对话没有逐条归档，保留的是各版工程和本地修改记录。

## 运行记录与适用范围

制作演示时保留了真实模型请求和返回记录，也使用过明确标示的模拟模式检查界面。公开视频对已有真实结果进行了回放和剪辑，未作为连续实时调用的证明。本地规则检查、模拟检查与真实接口记录分别保存，不能互相替代。目前没有足够的对照数据证明推荐精准率或内容传播效率提升比例。

API密钥只保存在本地后端配置中，不进入前端、公开仓库或下载包。真实模式会把描述和必要景点资料发送给所配置的服务；默认演示模式不调用真实模型。工具只按现有资料提供候选和文案初稿，事实核对与内容采用由使用者完成。
